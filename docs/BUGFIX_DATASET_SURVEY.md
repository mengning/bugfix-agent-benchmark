# Bugfix 数据集构成调查：从项目与缺陷到能力解释

状态：研究报告 v0.1（2026-10-20）。本报告用于确定数据集建设方向，不宣称新增 case 已完成本地复现，也不将本文的能力标签视为经过实验验证的结论。

## 1. 研究问题与结论

本报告回答三个问题：常见数据集为什么选特定仓库？为什么选特定缺陷？这些选择允许研究者对 Bugfix Agent 的能力作出何种解释？

**结论：一个可解释的 Bugfix case 不是“仓库 + Issue + 测试”三个字段的组合，而是一个测量设计。** 仓库提供软件和工作情境，缺陷设置需要克服的修复障碍，报告决定 Agent 可见的信息，验证证据决定能支持多强的能力结论。本文提出以下分析框架，而非引用某篇论文的既有公式：

```text
case 的解释力 = 目标能力 × 仓库情境 × 缺陷机制 × 信息条件 × 判定证据
```

乘号表示任一维缺失会限制解释力，不表示已有数值权重或可直接计算的总分。**缺陷类别不等于 Agent 能力。** 例如两个“缺失值”Bug，一个可能只需改条件判断，另一个可能必须识别跨库数据表示和统计前处理；仅凭标签不能推断它们测量同一种能力。

## 2. 现有数据集实际如何选题

| 数据集与来源 | 仓库选择逻辑 | 缺陷/任务选择逻辑 | 能合理解释的成绩 | 不能直接推出的结论 |
| --- | --- | --- | --- | --- |
| [Defects4J][defects4j] | 有真实修复历史、可重建 Java 版本与测试环境的项目 | 关联 Issue、单提交修复；人工移除无关改动；错误版的稳定触发测试在修复版通过 | 受控、可复现的程序修复能力 | 从自然语言报告独立诊断的完整 Agent 能力 |
| [BugsInPy][bugsinpy] | 可检出错误版/修复版并运行测试的 Python 项目 | 真实缺陷版本对及相关测试 | Python 项目中的受控修复能力 | 对其他语言和项目形态的泛化 |
| [SWE-bench][swebench] | 12 个有 Issue/PR 历史的流行 Python 仓库 | 从真实 Issue 与相关 PR 构造仓库级任务 | 从问题描述到补丁的综合解决率 | 细分定位、诊断、验证等能力的单独分数；所有 Issue 都是纯 Bugfix |
| [SWE-bench-Live][live] | 先按 Python、活跃度、Issue/PR 数量和许可证过滤，并扩大项目覆盖 | 较新的 Issue–PR 对，要求修复包含测试改动、构造可执行环境并重复检查测试行为 | 较新、可执行任务上的解决率 | 对低活跃度或没有测试补丁的真实缺陷的代表性 |
| [SWE-bench Pro][pro] | 有成熟开发实践的专业项目，包含不同应用领域；限制单仓库贡献量 | 偏重跨文件、长程工程任务，人工补全需求和审查测试；**并非只含 Bugfix** | 较复杂仓库级工程任务的解决率 | 日常 Bugfix 的自然频率或纯 Bugfix 能力 |

这些数据集的筛选条件不是可以照搬的“质量阈值”。例如 Star/PR 数能提高自动采集的可行性，却会改变目标项目总体；“必须新增测试”方便形成自动判据，却排除了开发者没有补测试的缺陷。[SWE-bench-Live][live] 的论文明确写出这些筛选条件；[SWE-bench Pro][pro] 则明确追求跨文件复杂任务。报告成绩时必须同时报告选择造成的外推边界。

## 3. 选仓库：仓库代表一种工作情境

对 Bugfix Agent 而言，仓库不是代码容器，而是任务的环境变量。至少需要描述以下正交维度：

| 维度 | 为什么影响测量 | 示例 |
| --- | --- | --- |
| 软件形态与领域 | 语言和依赖之外，还决定行为契约在哪里定义 | Web 框架的权限与状态、科学计算库的数值语义、可视化库的数据前处理 |
| 架构与状态边界 | 决定需要追踪局部函数还是跨模块、跨请求的因果链 | 单函数算法、异步回调、持久化状态与缓存 |
| 项目可观察性 | 测试、日志和文档越充分，Agent 越容易定位；这是难度来源之一 | 报告自带最小复现，或仅有用户症状 |
| 生态和时间 | Agent 对知名旧仓库可能已有记忆；新版依赖和新项目又有额外环境成本 | 旧版 Django 与近期项目不可直接混作同一难度 |

因此本仓库应把“项目形态”和“缺陷机制”分开标记。一个数据集若仅有 Python 小库，即使有很多 Bug 类别，也不能声称覆盖服务或多语言项目。相反，仅增加仓库数量但题目都只需改一个边界判断，也不足以测复杂诊断。

## 4. 选缺陷：缺陷代表需要克服的障碍

“真实缺陷”是必要条件，不是足够条件。以下四种任务提供不同的能力信号，且可在同一仓库里并存：

| 任务障碍 | 需要观察的 Agent 行为 | 自动测试能确认什么 | 主要混淆因素 |
| --- | --- | --- | --- |
| 症状与根因分离 | 沿调用链找到应修改的位置，而不是掩盖报错 | 给定复现不再失败 | Issue 已直接指出文件或根因 |
| 行为契约含多个边界 | 从示例归纳规则并处理反例 | 覆盖到的输入/输出正确 | 少量测试无法排除特判 |
| 状态或阶段间交互 | 追踪前一步修改对后一步的影响 | 指定状态序列通过 | 用例只覆盖一个执行顺序 |
| 修复与回归存在张力 | 修目标行为同时保留其他调用方行为 | 目标测试与已有回归测试通过 | 测试不充分或补丁改变未测语义 |

这里的“能力信号”是**假设**。若某例失败是依赖环境无法启动，不能据此说 Agent 缺少状态推理。若报告直接给出修复方案，成功也不能说明独立定位能力。[SWE-Bench+][plus] 报告了解法泄漏和弱测试的风险；[Solved Issues?][solved] 进一步指出测试通过的补丁可能与开发者期望的行为不一致。两篇研究的数字只适用于各自实验样本，不可直接套到本清单。

## 5. 三个原始上游 case 的逐例分析

本仓库在 [`datasets/swe-bench-lite/original-cases.txt`](../datasets/swe-bench-lite/original-cases.txt) 保存以下官方 SWE-bench Lite `test` split 的 instance ID。任务原文、基线提交及官方测试标识以[上游数据记录][lite]为准；这里不复制 gold patch 或 test patch。以下依据上游公开记录作**纸面分析**，尚未逐例构建容器或人工核验补丁正确性。

### A. `astropy__astropy-12907`：嵌套组合模型的可分离性

- **仓库为何重要**：Astropy 是科学计算项目；问题要求理解模型组合的结构语义，而不只是 Python 控制流。基线提交为 `d16bfe05a744909de4b27f5875fe0d4ed41ce607`。
- **原始缺陷**：报告展示平铺组合时矩阵正确，但将两个线性模型嵌入复合模型后，原本独立的输入/输出被误判为相关。记录包含 2 个 `FAIL_TO_PASS` 和 13 个 `PASS_TO_PASS` 测试标识。
- **测量假设**：主要观察嵌套结构语义理解与等价组合行为保持；不是“改了多文件所以测跨文件能力”。
- **判定边界**：通过两条目标测试只支持这些组合形态已修复；若要声称一般性的模型代数正确性，需另外验证更多嵌套形态。

### B. `django__django-12700`：调试信息中的嵌套敏感值

- **仓库为何重要**：Django 是服务框架，调试报告涉及安全相关的敏感数据清理；基线提交为 `d51c50d836c5cf8db5566da17963f871be554615`。
- **原始缺陷**：顶层字典的 `secret`/`token` 会遮蔽，但列表、元组等嵌套容器里的同类值可能原样泄露。上游记录含 1 个 `FAIL_TO_PASS` 和 77 个 `PASS_TO_PASS` 标识。
- **测量假设**：主要观察递归数据结构上的安全契约与副作用控制，而非单纯“权限 Bug”。
- **判定边界**：原报告已指出 `cleanse_setting()` 与可能的遗漏机制，故此例**不适合**单独证明 Agent 能自主定位根因。测试通过也不等于覆盖所有容器、自定义对象和泄露渠道。

### C. `mwaskom__seaborn-3010`：拟合阶段对缺失数据不稳健

- **仓库为何重要**：Seaborn 涉及可视化、统计转换和 NumPy 数值运算之间的数据流；基线提交为 `0f5a013e2cf43562deec3b879458e59a73853813`。
- **原始缺陷**：`PolyFit` 遇到含 `None` 的输入，在拟合链路抛出线性代数异常。上游记录含 1 个 `FAIL_TO_PASS` 和 2 个 `PASS_TO_PASS` 标识。
- **测量假设**：主要观察 Agent 能否分清表面异常位置与需要处理缺失值的数据前处理阶段，并保留正常拟合行为。
- **判定边界**：仅有少量回归测试，不能仅凭通过率声称所有缺失值模式和数值稳定性均正确。

三个 case 的差异不是“挑三个不同仓库凑多样性”，而是分别提供**结构语义、安全递归契约、跨层数据流**三种修复障碍。它们目前只是一组用于检验能力框架的研究样例，**不是统计代表样本，也不是新榜单**。

## 6. 反例：为什么真实题也可能不适合某项能力测量

- `django__django-13551` 的原始报告直接建议将邮箱纳入密码重置 token 的哈希值。它可用于验证最终行为，但不能据成功推断 Agent 独立发现了修复策略。
- `pytest-dev__pytest-7373` 的报告直接指出缓存键及建议删除缓存。它也不适合作为“未知根因定位”题。
- `psf__requests-1963` 有清晰的多跳重定向状态错误，理论上很适合阶段间状态推理；但上游记录的 `FAIL_TO_PASS` 包含多条与摘要看起来不直接相关的测试，入正式的能力诊断集前要逐条审查测试归属。

反例说明：**题目能跑、测试能过，不等于题目能支撑我们想宣称的能力。** 报告的信息含量和测试的判定范围必须一起解释。

## 7. 对本仓库的研究结论与后续验证

1. 保留 `bugfix-v1` 的三条自建 fixture 作为 Runner/评分器和基础行为的可控用例；它们不代表真实项目分布。
2. 把本报告的三条上游 case 放在 SWE-bench Lite 的**独立选择文件**，而非改写自建 `manifest.jsonl`。使用现有 `fetch_swe_bench.py --instances-file` 读取官方记录；评分口径仍按对应上游协议，不把两类分数相加。
3. 后续新增正式的 Bugfix 专项集时，为每例分别记录：项目情境、缺陷机制、Agent 可见信息、预期操作障碍、验证证据、无法支持的能力结论。这些标签先是研究假设，再由实际轨迹和对照任务检验。
4. 在报告“某能力较强/较弱”之前，至少需要排除环境失败、提示中答案泄漏、弱测试、项目熟悉度等替代解释。当前三例不足以完成这一步。

本报告的局限：原始 case 分析基于上游公开记录，不等于对其全部论文、历史讨论和环境的独立复现；三例是说明分析框架的实例，不可用来估计总体成功率或项目分布。本文由 AI 辅助检索与归纳，引用的文献结论应以链接原文为准。

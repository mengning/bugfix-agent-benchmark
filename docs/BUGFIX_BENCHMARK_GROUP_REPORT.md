## 二、我们究竟在测什么：结果金标准、轨迹诊断与评测边界

### 2.1 Bugfix Agent 属于哪种测评

我们的主任务是**真实仓库上的 Issue-to-patch 端到端修复**：给 Agent 一个冻结在缺陷修复前的仓库和一份问题描述，让它自主读代码、定位、修改并提交 patch；在独立环境里判断目标缺陷是否消除且旧行为没有回归。它不是单纯的代码补全、测试生成、PR 数量统计，也不是仅根据“思考过程像不像专家”打分。

| 层次 | 问题 | 判定方法 | 本项目现状 |
| --- | --- | --- | --- |
| **结果金标准（主指标）** | 修好了吗？ | 隔离环境应用 patch；检查修复前失败的目标测试是否通过、原本通过的回归测试是否保持通过；空 patch 失败 | 自建题已有验证器；SWE-bench 题使用其官方 harness。125 题试评未完成 |
| **轨迹诊断（解释指标）** | 为什么成功或失败？ | 复核读取证据、复现、定位、修改、测试与纠错等可观察事件；不要求唯一正确操作顺序 | 已定义观察维度，尚无经校准的轨迹分数 |
| **运行表现（约束指标）** | 成本、耗时和稳定性如何？ | 固定预算记录墙钟时间、Token/费用、工具调用、重试、超时及多次运行结果 | 尚无完整可比的正式分数 |

这里的“**标准答案**”有两层：上游参考修复（gold patch）用于证明题目可解、核对题面和测试；真正给 Agent 评分的是**独立的行为判据**，而不是逐字比对 gold patch。不同正确实现都应有机会通过。SWE-bench 的 `FAIL_TO_PASS` 检查缺陷行为修复，`PASS_TO_PASS` 检查已有行为不回归；测试还需人工审查是否覆盖 Issue 的真实要求。参考修复通过、原始错误版失败、空 patch 失败，是正式题的发布闸门。

轨迹不能替代结果金标准：一次有效修复可以有多条合理路径；Agent 改变原计划可能是根据新证据纠错。我们只在**结果确定且运行环境有效**之后，分析失败发生于问题理解、定位、修改还是验证；基础设施失败单独记录。安全越界（例如读取隐藏测试、泄露凭据）是独立红线，不能被高平均通过率抵消。

### 2.2 三类题，各自回答不同问题

| 题集用途 | 作用 | 现在能否宣称已有正式成绩 |
| --- | --- | --- |
| 控制/回归题 | 验证 Agent 调用、补丁应用、评分器及版本升级不退化 | 自建 Bugfix-v1 有 3 题可运行；只证明链路，不代表行业能力 |
| 公开协议对照题 | 在相同数据集版本和官方判据下，与公开 Agent 结果建立可比坐标 | 已有 Lite 125 题部分预测与中断试评；目前不能作完整横向排名 |
| Bugfix 专项能力题 | 按业务情境和缺陷机制解释“Agent 擅长/不擅长修哪类 Bug” | 已有候选与选题框架，跨来源题尚未完成统一准入和正式评分 |

我们计划统一**任务入口、产物格式、运行记录和报告口径**，但不强行用一个验证器给所有语言与来源打分。每题固定为：

```text
修复前仓库（repo + base commit + 环境）
  + Agent 可见的 Issue（现象、期望、复现边界）
  + 隐藏的标准修复/独立测试与评分配置
  → Agent patch → 隔离复现与评分结果
```

来源不原生提供 Issue 的历史缺陷对，只有补齐**修复前可信且不泄漏答案的问题描述**后，才可进入这一统一入口。JSON 候选清单只是索引，不等于已经具备 repo、Issue、gold 和可执行评分器的正式题。不同来源仍须保留原协议和分层结果，不把 APR、视觉任务、Issue-to-patch 的通过数直接相加。

## 三、数据集如何建成：调研、业务分类、选题与当前工作量

### 3.1 从公开数据集学到了什么

我们调查了 SWE-bench、Pro、Live、多语言集，以及 Defects4J、BugsInPy、BugsJS 和 CI/并发缺陷集；详细记录见[数据集构成调查](BUGFIX_DATASET_SURVEY.md)与[跨来源选题逻辑](MULTI_SOURCE_SELECTION.md)。

| 来源 | 借鉴的做法 |
| --- | --- |
| SWE-bench 系列 | 用真实仓库、修复前 Issue 和测试组成完整的修复任务。 |
| SWE-bench Pro | 从不同软件工作情境选仓库，再检查题目与测试是否一致。 |
| 历史缺陷集与专题集 | 保留错误版、参考修复和触发测试，补充并发、安全等不同缺陷。 |

Pro 的后续审计提醒我们：题目来自真实项目，也可能存在描述不清或测试不合理的问题。因此，**不能只收集 Issue 数量；每题还要验证“原始代码会失败、参考修复能通过、没有修复不能通过”**。来源没有修复前 Issue 的，必须补齐可信的问题描述，才适合用于统一的 Bugfix Agent 测评。

### 3.2 我们怎样选仓库和 case

先按故障影响选择不同类型的仓库，再从仓库中选择能明确复现和评分的 Bug。这样每类题都有清楚的能力目标。

| 仓库类型 | 想选的 Bug | 主要测什么 |
| --- | --- | --- |
| 用户应用 | 页面、交互或前后端状态出错 | 能否从用户看到的症状找到原因 |
| 业务服务 | 权限、敏感数据或持久化出错 | 能否守住业务和安全规则 |
| 开发者工具 | API、构建或配置出错 | 能否理解兼容性和工具链 |
| 专业软件 | 数值或数据结构结果出错 | 能否理解领域行为，而非只消除报错 |

同一类仓库中，再选不同的修复难点，例如边界条件、跨模块状态、并发或资源恢复；同时记录 Issue 提供了多少线索、修复是否需要跨文件。**最终一道正式题必须具备：修复前仓库及版本、Agent 可见的 Issue、参考修复、可执行的独立评分器。**评分前检查 Issue 与测试是否一致，并隔离参考答案。没有通过检查的题留在候选池，不计入正式成绩。

## 四、下一阶段如何交付

1. **补齐 125 题评分并固定实验记录。** 恢复可用的评分资源，复评尚无判定的 19 题；保存完整官方 `results.json`、Agent/模型配置、预算、补丁快照与失败分类。在此之前不报正式整体通过率。
2. **把候选题晋升为正式题。** 优先处理逐例审查的 `nominated` 和 Lite 诊断选择，逐题补修复前 Issue、基线 commit、gold、目标/回归判据、三方回放和环境说明；不满足者明确标为 `hold/invalid_case/infrastructure_error`。
3. **形成可解释的 Bugfix 专项集。** 发布每题为何代表一种业务故障与修复障碍；报告按仓库情境、机制、跨度和信息条件分层，另设未参与开发调参的留出仓库。只有相同输入协议、数据集版本与评分规则下才作同行横向比较。
4. **再补轨迹与表现层。** 在结果可靠后针对成功/失败题记录和复核可观察轨迹、时间、成本与重复运行稳定性；不以未经校准的模型裁判分替代结果金标准。

## 五、组会口头汇报（约 4 分钟）

> 第一，先报真实结果。Bugfix Agent 对 SWE-bench Lite 的 125 题生成了预测：61 题经官方 harness 判定成功，31 题提交了代码但失败（其中 21 题改了目标项目实现代码），1 题只改文档且失败，13 题空 patch，19 题虽有 patch 但云端评分中断。已评分且提交代码 patch 的条件成功率是 61/92，即 66.3%；125 题整体目前只能说至少 61 题成功。后续重试确认 Modal 账户达到费用上限，尚无完整 125 题分数，而且 114 题来自 Django，不能与完整 300 题榜单直接比较。
>
> 第二，我们的 Bugfix Agent 测评定位是仓库级 Issue-to-patch：结果金标准先判断修复前失败的行为是否变对、原有行为是否回归；轨迹用于解释 Agent 卡在哪一步；成本和稳定性是运行约束。gold patch 是验证题目有效性的参考，不是要求 Agent 复写的唯一答案。正式 case 必须有修复前仓库、Agent 可见 Issue、标准修复与独立评分器。
>
> 第三，我们调研了 SWE-bench 系列、Pro、Live、多语言集及 Defects4J、BugsInPy、BugsJS、CI/并发专题集。Pro 告诉我们先覆盖不同工作情境，但其后续审计也说明题面与测试可能失配。因此我们先按用户应用、业务服务、开发者工具和专业领域软件的故障后果选仓库，再按缺陷机制、跨度、输入信息与判据选题。已形成 3 题自建运行闭环、Lite 300 ID 索引与 84 题诊断选择、17 题跨来源逐例审查、176 题去重研究候选池。这些是不同成熟度层级，不是 176 道可评分正式题。
>
> 下一步先补齐 19 题官方评分，再把候选题逐道过错误版失败、gold 通过、空 patch 失败、题面—测试对齐和环境复现闸门，形成既可比较又能解释 Agent 能力差异的 Bugfix 专项集。
